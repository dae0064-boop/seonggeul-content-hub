# 결정 기록

## 2026-08-21 — 클라우드 차단은 환경 설정으로 풀 수 있다 (중요)

앞서 "네이버 API·Apify·OpenAI는 클라우드에서 못 쓴다"고 결론냈는데, **틀렸다.**
환경(cloud environment)의 네트워크 접근 수준을 바꾸면 된다.

- 접근 수준은 네 가지: **None / Trusted(기본) / Full / Custom**
- **Custom**을 고르고 `Allowed domains`에 도메인을 한 줄씩 적으면 열린다.
  `*.` 로 서브도메인 전체 지정 가능.
- "Also include default list of common package managers"를 **체크해야** 기존 것이 유지된다.
- **`*.frame.claudeusercontent.com`을 반드시 포함해야 한다.** 빠지면 세션이
  아티팩트를 읽지 못한다. 매일 원고 링크가 아티팩트라서 필수다.
- 이걸 열면 `api.openai.com` 뿐 아니라 `openapi.naver.com`, `api.apify.com` 도
  같이 풀린다. 앞선 제약이 사라진다.

### 시크릿 취급 — 주의

- 문서가 **환경 변수에 API 키를 넣지 말라고 명시**한다. 클라우드 환경에는 전용
  시크릿 저장소가 없고, 그 환경을 쓰는 사람은 값을 읽을 수 있다.
- 개인 계정이라 실질 위험은 낮지만, Pro/Max 계정의 세션 공유는 **Public**이 될 수
  있으므로 완전히 무시할 수는 없다.
- 완화책: **OpenAI 쪽에서 월 사용 한도를 낮게 걸어둔다.** 키가 새도 피해가 한도까지로
  제한된다. 이게 실질적인 방어선이다.

## 2026-08-21 — 이미지는 도구를 나눈다

- **사진풍 삽입 이미지(텍스트 없음)** → GPT 이미지 API. 이쪽이 낫다.
- **카드뉴스(한글 텍스트 필수)** → 직접 HTML로 렌더링한다. 이미 Chromium과
  Playwright가 깔려 있고 Google Fonts 한글 웹폰트에 접근된다. 생성 모델은 한글
  텍스트를 정확히 못 그리므로 글자가 들어가는 카드는 렌더링이 정확하고 무료다.
- GPT Image 1은 2026-10-23 지원 종료 예정이므로 새로 쓰지 않는다.

## 2026-08-21 — 줄바꿈 기준 재정립 (교차 검토 후 수정)

다른 도구(코덱스)의 교차 검토를 받아 앞선 기준을 고쳤다. 지적이 타당했다.

- **글자 수는 목표가 아니라 상한선이다.** "20자에 맞춰 끊는다"는 앞선 기준을 폐기했다.
  글자 수를 맞추려다 `신청 화면` 같은 의미 덩어리를 쪼개는 게 더 큰 오류다.
- 새 기준: **12~20자 기본, 최대 24자, 꼭 필요하면 26자.** 문단은 2~4줄.
- 너무 잘게 쪼개는 것도 문제다. 첫 원고 6편이 평균 10.7자로 과도하게 짧아
  전부 다시 붙였다(평균 17~18자로 조정). 스크롤만 길어지고 호흡이 끊긴다.
- **제목은 30자 이내.** 네이버 모바일 검색결과가 그 부근에서 잘린다.
  실측: 현재 장학금 글 제목 37자, 코덱스 수정안 35자 — 둘 다 잘린다.

## 2026-08-21 — 경험은 지어내지 않는다 (앞선 조언 철회)

- 원고에 경험 자리를 표시할 때 **채울 문장을 예시로 써주지 않는다.** 예시를 주면
  그대로 베껴 쓰게 되고 그게 곧 허위 경험이 된다. 앞서 "동생이 대학에 들어간 해라…"
  같은 예시 문단을 제안한 것은 잘못이었다.
- 실제 경험이 없을 때는 **조사 과정을 밝힌다.** "재단 공지와 기존 글을 대조해보니
  가장 헷갈리는 부분은 …이었습니다" 처럼. 이것도 본인의 실제 작업이므로 쓸 수 있다.
- **철회한 주장**: "내부링크가 체류시간을 두 배로 만들고 블로그 지수에 직접 영향을
  준다" — 근거 없는 단정이었다. 내부링크는 여전히 권장하되 효과를 수치로 말하지 않는다.
- **철회한 주장**: "핵심 키워드를 무조건 제목 맨 앞에" — 필수 규칙이 아니다. 권장이다.

## 2026-08-21 — 모바일 가독성 기준

- 읽는 사람 대부분이 모바일이다. **네이버는 한 줄 20자 내외에서 강제 줄바꿈**한다.
  사용자가 25~35자로 알고 있었으나 확인 결과 20자가 통용 기준이다.
- **티스토리는 강제 줄바꿈을 하지 않는다.** 구글이 문서 구조를 읽는데 `<br>`를
  남발하면 구조가 나빠진다. 대신 문단을 2~3문장으로 짧게 끊는다.
- 두 채널을 같은 방식으로 쓰지 않는다. 이게 핵심이다.
- 공통: 6줄 이상 문단 금지, 도입 3줄은 특히 짧게, 나열은 목록·비교는 표.
- `scripts/brief-render.mjs` 를 만들었다. 그날 원고 폴더의 마크다운을 읽어
  페이지로 만든다. 문단 안 줄바꿈을 `<br>`로 살려 20자 개행이 화면에 그대로 보인다.
  매일 자동 실행도 이 도구를 쓴다.

## 2026-08-21 — 역할과 발행 운영기준

- **역할**: SNS 마케터 겸 개발자 비서. 사용자는 SEO와 블로그 구조를 모른다는 전제로
  설명한다. 원고 제작을 통째로 맡는다.
- **1순위 채널**: 네이버 블로그(검색 유입 + 홈판), 티스토리(구글 노출 + 애드센스 승인).
  브랜드 구축이 목적이므로 주제를 흩뜨리지 않는다.
- **하루 편성**: 네이버 3편(검색형 2 + 홈피드형 1), 티스토리 3편(롱폼/가이드/비교),
  이미지 8~10장 프롬프트, 인스타 카드뉴스 프롬프트. 상세 기준은
  `standards/발행-운영기준.md`.
- **속도를 조절하기로 함**: 첫날부터 하루 3편은 네이버 저품질·애드센스 거절 위험이
  크다. 1주차 1편 → 2주차 2편 → 3주차부터 3편을 권고했다.
- **발행 방식**: 복사·붙여넣기까지는 사용자가 한다. 티스토리 API가 종료됐고 네이버
  자동 로그인은 계정 제재 위험이 있어, 발행 직전 사람이 한 번 보는 편이 낫다.
- **전달 방식**: 매일 결과를 Artifact 링크로 낸다(주소 고정, 즐겨찾기 하나). 원본은
  드라이브에 쌓는다. 운영기준 설계서:
  https://claude.ai/code/artifact/f87ee1c0-2340-4ab1-930e-05a8f2396f7a
- **미결**: 매일 9시 실행 위치 — 클라우드(네이버 API·인스타 못 씀) vs 사용자 PC(전부 씀).

## 2026-08-21 — 발행 자동화: 티스토리는 막혔고 네이버는 조건부

- **티스토리 Open API는 2024년 2월에 완전 종료됐다.** 글쓰기·수정·첨부·댓글 전부.
  신규 발급도 기존 키도 못 쓴다. 다시 알아볼 필요 없다.
  → 티스토리 자동 발행은 브라우저 자동화 외에 방법이 없다.
- **네이버 블로그 글쓰기 API는 남아 있다.** 단 '네이버 아이디로 로그인' 연동으로
  access token을 받아야 한다. 검색 API와는 다른 계열이다.
  → **미확인: 임시저장(draft) 지원 여부.** 네이버 개발자 문서가 이 환경에서
  막혀 확인 못 했다. 사용자 PC에서 확인할 것.
- **브라우저 자동화는 마지막 수단으로 남긴다.** 네이버가 자동화 로그인에 민감해
  계정 제재 위험이 있다. 블로그 계정 손실은 되돌릴 수 없으므로 감수할 위험이 아니다.
- **당분간 '붙여넣기 완성본' 방식으로 간다.** 티스토리 HTML 모드에 그대로 붙여넣을
  수 있는 형태로 글을 뽑아준다. 발행 전 사람이 한 번 보게 되는 것도 이점이다.

새 항목을 맨 위에 추가한다. 각 항목은 무엇을 정했는지와 왜 그렇게 정했는지를 남긴다.

## 2026-08-21 — 드라이브 폴더 구조 재편

- 기준(루트) 폴더는 기존 `내 드라이브/성글벙글 원소스 멀티콘텐츠 자동화 구현/`을 그대로 쓴다.
  새 폴더를 만들지 않는다.
- 재편 이전에 있던 자료 3건(운영기준 문서, `00_발행일정표/`, `2026-08-13_국가장학금` 폴더)은
  삭제하지 않고 `_archive/`로 옮겼다. 필요하면 거기서 꺼내 쓴다.
- 폴더는 번호 접두사로 정렬한다: `00_기준문서`, `01_작업`, `02_발행일정표`, `09_메모리`.

## 2026-08-21 — 동기화 방식

- 컴퓨터 세 대(집·회사·노트북) 모두 구글 드라이브 데스크톱 앱이 설치되어 있어,
  로컬 폴더 복사 방식으로 동기화한다. API 업로드보다 빠르고 오프라인에서도 동작한다.
- 삭제는 전파하지 않는다(`rsync --update`, `--delete` 없음). 한쪽에서 실수로 지운
  파일이 다른 컴퓨터에서 사라지는 사고를 막는 편이, 지운 파일이 되살아나는
  불편보다 낫다고 판단했다.
- git이 정본이다. 드라이브는 컴퓨터 간 전달 수단이자 백업이다.
